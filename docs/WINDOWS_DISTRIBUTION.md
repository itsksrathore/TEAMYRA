# Windows Distribution

TEAMYRA Phase 7 packages the local-first control plane as a Windows desktop application without requiring end users to install Python.

## Target layout

The packaged Electron app owns the UI and embeds one standalone Python core executable as an extra resource:

```text
TEAMYRA.exe
resources/
  app.asar
  teamyra-core/
    teamyra-core.exe
```

At runtime the desktop process sets:

```text
TEAMYRA_ROOT=<Electron userData>/runtime
TEAMYRA_CORE_EXE=<resources>/teamyra-core/teamyra-core.exe
```

Runtime state therefore stays outside the installation directory:

```text
runtime/
  jobs/
  logs/
  tasks/
  worktrees/
  memory/
  profiles/
```

Provider credentials remain in the provider's normal native home or in TEAMYRA's isolated runtime profiles. They must never be bundled into the installer.

The desktop process also owns the localhost TEAMYRA MCP lifecycle. On startup it ensures `http://127.0.0.1:8787/mcp` is available. Closing the main window hides the UI instead of terminating the process, so detached jobs, MCP access, and embedded-agent state continue in the background. Starting TEAMYRA again focuses the already-running single instance. Explicit application quit/update shutdowns stop the MCP child process that the desktop started.

## Packaged core

`bridge/teamyra_entry.py` is the single executable entrypoint.

Normal invocation delegates to the TEAMYRA CLI. Internal modes let the same binary host detached worker processes without shipping Python source scripts as separate executables:

- `__runner`
- `__conductor-monitor`
- `__review-monitor`
- `__failover-monitor`
- `__desktop-api`

The core is built with PyInstaller as a one-file Windows executable. Dynamic imports used by internal modes must be listed as hidden imports in the PyInstaller spec.

Development mode continues to execute the Python source tree directly. Packaged mode must use `TEAMYRA_CORE_EXE`.

## Electron packaging

Use electron-builder with Windows NSIS.

The bundled core should be copied with electron-builder `extraResources` into:

```text
resources/teamyra-core/teamyra-core.exe
```

The production desktop build must not fall back to a system Python installation if the bundled core is missing. A missing bundled core should be treated as a packaging error.

Recommended Windows installer behavior:

- x64 NSIS installer
- assisted install rather than silent one-click install
- allow the user to choose installation directory
- create Start Menu shortcut
- optional desktop shortcut
- do not request elevation unless the chosen install path requires it
- no runtime credentials, logs, jobs, worktrees, or profiles inside the installer

## Build order

A Windows release build should run these gates in order:

1. Python compile and unit tests.
2. Desktop JavaScript syntax checks.
3. Renderer bundle build.
4. PyInstaller build of `teamyra-core.exe`.
5. Core CLI smoke test.
6. Packaged-core desktop API smoke test using a temporary `TEAMYRA_ROOT`.
7. electron-builder unpacked build.
8. Launch the unpacked desktop app and verify the renderer loads.
9. Verify provider auto-detection still sees existing Claude/Codex/Antigravity native sessions.
10. Verify one-click TEAMYRA MCP registration and connection verification for installed provider CLIs.
11. Close the main window and verify the local MCP plus an active job continue while the UI is hidden.
12. Relaunch TEAMYRA and verify the existing background instance is restored rather than duplicated.
13. Verify one core-backed desktop action works without Python on PATH.
14. Build NSIS installer.
15. Install into a test directory and launch the installed app.
16. Verify runtime data is written under Electron userData rather than Program Files.
17. Uninstall and verify user runtime data is not silently destroyed.

## CI

Foundation validation should run on both Windows and Linux. Windows is mandatory because TEAMYRA depends on Windows process creation, provider CLI discovery, PTY behavior, PyInstaller packaging, and NSIS.

A distribution workflow should build the Windows artifacts on `windows-latest` and upload:

- `teamyra-core.exe`
- unpacked desktop artifact for debugging
- NSIS installer
- release metadata generated by electron-builder when update publishing is enabled

Release publishing should remain separate from ordinary pull-request checks.

## Updates

electron-builder's supported Windows auto-update path uses the NSIS target with `electron-updater`.

Do not enable automatic installation before a signed release channel exists. During development, update checks should be disabled or limited to explicit test channels.

A production update pipeline should include:

- deterministic version source
- GitHub Release or another configured update provider
- generated update metadata
- Windows code signing
- staged/test release channel before stable
- explicit logging for download/install failures

## Signing

Unsigned development installers are acceptable for local verification but will trigger Windows reputation warnings.

Before public release, use a Windows code-signing certificate and sign both the Electron installer/application and, where practical, the bundled core executable.

Signing secrets belong only in CI secret storage. They must never be committed to the repository.

## Release acceptance

Phase 7 Windows distribution is considered complete only after all of these are true:

- clean checkout can build the core and desktop artifacts
- no separate Python install is required by the packaged app
- native provider auto-detection works
- isolated managed provider profiles still work
- embedded terminal works
- jobs survive desktop restarts according to crash-recovery rules
- NSIS installer installs and launches successfully
- runtime data is outside the install directory
- CI builds the Windows artifact
- update pipeline is tested on a non-stable channel
