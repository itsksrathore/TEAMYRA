## C-2 integration proposal (SUGGESTIONS; NOT PRESENT API)

A lead chat should reuse the existing provider, exact-text parser, bounded tool-result bridge, permission check, job scanning and IPC patterns; avoid creating a second independent browser driver or unrestricted shell path. Suggested versioned envelope: `{version:1,conversation_id:string,turn_id:string,workspace:string,provider_profile_id:string,request:{tool:string,args:object},deadline_ms?:number}`; response `{version:1,turn_id:string,ok:boolean,result?:object,error?:{code:string,message:string},message_id?:string}`. Enforce workspace authorization on **every** tool, persist a unique turn/tool ID and phase before dispatch, and distinguish send failure/unknown outcome from safe retries. Separate interactive lead conversations from delegated job ownership. A proposed IPC seam is `teamyra:lead-*` in main/preload/renderer, backed by an authenticated core action and existing workspace service; this is an architectural suggestion, not an existing function.

## Risks / decisions to resolve

Rendered text may be incomplete or contain UI copy controls; raw replies may be unavailable on non-ChatGPT sites. Two stable polls can still end before later server edits; be conservative with completed/limit/challenge states. Crash after pre-dispatch persistence yields an unknown tool outcome; never blindly replay mutating actions. Job ownership, profile switching, multiple lanes, renderer/browser lifecycle and permission elevation must remain independently guarded. Current parse-failure threshold can terminate jobs for unescaped Windows JSON paths; C-2 should supply short explicit parse errors rather than silently repairing arbitrary actions. Define lead-chat persistence/ID semantics, cancellation, backpressure, UI visibility, and how to observe job vs chat output before implementation.
