## Stage 1 implementation reuse guidance (DESIGN / PLAN; NOT IMPLEMENTED)

S1-2 `LeadSession` should reuse existing adapter methods (`assistantSnapshot`, `waitForAssistantReply`, `rawReplyText`, `parseToolRequestDetailed`, `sendTask`), bounded results, `JobProcesses`, `JobInspector` and workspace permission checks, without running a second independent browser driver or reusing `runDelegatedJob` as the lead loop. Keep the existing one-line `TEAMYRA_TOOL_REQUEST {json}` / `TEAMYRA_TOOL_RESULT {json}` protocol **unchanged**; no new wire version, envelope or parser protocol. Lead sessions own dedicated `#lead` tabs, not job lanes; only a finished tool-request reply triggers execution. The design assigns core orchestration routing to S1-1 `lead.tool` (an allowlisted `server.tool_call` mapping), while S1-4 adds specified lead IPC and ensures lead providers do not scan job queues. Preserve per-tool workspace authorization, approvals, persisted state and unknown-outcome handling on interruption.

## Risks / decisions to resolve

Rendered text may be incomplete or contain UI copy controls; raw replies may be unavailable on non-ChatGPT sites. Two stable polls can still end before later server edits; be conservative with completed/limit/challenge states. Crash after pre-dispatch persistence yields an unknown tool outcome; never blindly replay mutating actions. Job ownership, profile switching, multiple lanes, renderer/browser lifecycle and permission elevation must remain independently guarded. Current parse-failure threshold can terminate jobs for unescaped Windows JSON paths; the existing tool-request parser and future S1-2 `LeadSession` should report concise parse failures without executing ambiguous actions. C-2 concerns code intelligence only. Define lead-chat persistence/ID semantics, cancellation, backpressure, UI visibility, and how to observe job vs chat output before implementation.
